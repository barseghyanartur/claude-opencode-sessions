# Design

## Goal

Continue work started in GitHub Copilot CLI inside Claude Code, without
spending tokens on browsing. `/copilot-sessions:import` turns this
repository's Copilot CLI sessions into Claude Code conversations. After
that, Claude Code's own `/resume` picker is the browsable list, and Enter
loads a session.

This is the third plugin in this monorepo, alongside `opencode-sessions`
(SQLite-backed) and `codex-sessions` (JSONL rollout files). It shares no
code with either — different source formats — but follows the same shape:
`models.py` / `scope.py` / `importer.py` / `import_command.py` /
`render.py` / `cli.py`, and is architecturally closest to `codex-sessions`
(pure filesystem, no database opened).

## Copilot CLI's on-disk format (reverse-engineered, not a published schema)

Verified against three real sessions produced by Copilot CLI 1.0.89/1.0.90
installed for this purpose (two with real conversations, one empty).

- **Location:** `$COPILOT_HOME/session-state/<uuid>/`. `$COPILOT_HOME`
  defaults to `~/.copilot` (Copilot CLI's own env var; see
  `copilot help environment`).
- **`workspace.yaml`**: flat `key: value` scalars — `id`, `cwd`,
  `git_root`, `repository`, `host_type`, `branch`, `client_name` (e.g.
  `github/cli`), `name` (the session's title, generated by Copilot CLI
  itself — absent on a session with no real conversation), `created_at`,
  `updated_at`. Read with a minimal line parser (`locate.read_workspace_yaml`)
  rather than a YAML library, since every field used here is a plain
  scalar and this keeps the package dependency-free like its siblings.
- **`events.jsonl`**: one JSON object per line,
  `{"type", "data", "id", "timestamp", "parentId"}`. Types read:
  - `session.start`: `data.copilotVersion`, read as `Session.version`.
  - `user.message`: `data.content` is the raw text the user typed.
    `data.transformedContent` — what's actually sent to the model, wrapped
    in a `<current_datetime>…</current_datetime>` block and similar — is
    **not** used; unlike Codex, the raw field needs no further filtering.
  - `assistant.message`: one per model step. `data.content` is its text
    (often empty on a tool-only step) and `data.toolRequests` is a list of
    `{toolCallId, name, arguments}` tool calls made in that step — both are
    folded into one `Message` with multiple `Part`s, matching opencode's
    "one message, several parts" shape rather than Codex's one-event-per-part
    shape. `data.reasoningText` / `data.reasoningOpaque` are dropped, like
    Claude Code's own thinking blocks.
  - `tool.execution_complete`: paired with its pending tool call by
    `toolCallId` (set when the matching `toolRequests` entry was parsed),
    filling in `data.result.content` as output and `data.success` as
    status. A call whose completion event never arrives (e.g. a denied
    permission) stays `status="pending"` and renders with no output —
    graceful, not an error.
  - Not read: `system.message` (the system prompt), every `session.*` /
    `model.*` / `permission.*` event, and `tool.execution_start`
    (redundant with the `toolRequests` entry already captured from
    `assistant.message`).
- **Not used at all: `session-store.db`.** Copilot CLI also keeps a SQLite
  index (`sessions`, `turns` — with clean `user_message`/`assistant_response`
  columns — `checkpoints`, and others) at `$COPILOT_HOME/session-store.db`.
  Every field this importer needs is already in `workspace.yaml` and
  `events.jsonl`, so the database is never opened — read-only, no
  database, no CLI call, consistent with `codex-sessions`. A session with
  no real conversation (just `session.start`/`session.shutdown`) has no
  row in this database at all, which is one reason the filesystem, not the
  database, is the source of truth for which sessions exist.

## Import rules

Same as the sibling plugins, since `importer.py` is only lightly adapted:

- **Target directory:** in the hook, the directory of the running
  session's `transcript_path`. From the terminal, derived as
  `~/.claude/projects/<path with non-alphanumerics → "-">` (respects
  `CLAUDE_CONFIG_DIR`), or set with `--claude-project-dir`.
- **Content:** user text, assistant text, and each tool call as a
  `→ tool: `args`` line (output only with `--with-tool-output`).
  Consecutive assistant steps are merged, so turns alternate. A header
  naming the Copilot session is prepended to the first user turn.
- **Transcript entries:** a `custom-title` entry (`[copilot] Title`, with a
  `copilotImport` marker holding the Copilot session id, content hash and
  suffix), then a `parentUuid` chain of `user` / `assistant` entries.
  Assistant messages use model `<synthetic>`, so resuming doesn't switch
  your model.
- **No duplicates:** the Claude session id is `uuid5(namespace, "<copilot
  id>:<sha256 of the turns>")`. Unchanged content maps to an existing file
  and is skipped; changed content gets the next free `(N)` suffix. Files
  are written to a temp name and hard-linked into place, which fails
  instead of overwriting.
- **Skipped:** sessions with no conversation text (Copilot CLI records
  these too, e.g. a session opened and closed without a prompt).

## Decisions

- **Python ≥ 3.10, standard library only.** `uv` and hatchling for
  development; tests live in `src/claude_copilot_sessions/tests`.
- **Naming:** PyPI package `claude-copilot-sessions`; plugin
  `copilot-sessions` in marketplace `barseghyanartur`, hence
  `/copilot-sessions:import`.
- **No model-driven skills.** Same reasoning as the sibling plugins —
  they'd cost tokens on every use.
- **No SQLite dependency**, even though `session-store.db` exists and
  mirrors `workspace.yaml`/`events.jsonl` in a more structured shape
  (`turns.user_message` / `turns.assistant_response`). Opening it would
  add a second source of truth to keep in sync and wouldn't provide tool
  call detail (`events.jsonl` still would be needed for that), so the
  filesystem alone is used, consistent with `codex-sessions`.

## Risks

- **Copilot CLI's session format is undocumented and young.** Reverse
  engineered from three real sessions produced by versions 1.0.89/1.0.90;
  a future release could rename fields or change how `toolRequests` /
  `tool.execution_complete` pair up. Unrecognised event types are skipped
  rather than raising, but their content would be silently dropped until
  this package is updated.
- **Claude Code's transcript format is internal.** Same risk as the
  sibling importers; the tests pin the written shape.
